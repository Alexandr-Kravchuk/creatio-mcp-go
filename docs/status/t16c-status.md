## How parity is checked

`scripts/compare-workspace-tools.py` runs clio 8.1.0.142 (`dotnet clio.dll mcp-server`) and this server in
separate temp homes (`CLIO_HOME`, `HOME`, `TMPDIR`) on the same calls through `clio-run`, and compares:
answers (JSON as data; home path, clio's `correlation-id`, temp folder names masked), every file under the
scenario's folder (bytes and mode; GUIDs numbered in order of appearance, Microsoft JSON dates masked), and,
with a fake Creatio site per side, every request both sent (JSON bodies as data; an uploaded zip by its
entries and each .gz package by its decoded files). Requests clio sends from a Parallel.ForEach (the
configuration and Autogenerated folder downloads, add-item-model's schema reads) and their "Run download" log
lines are compared sorted within each run, because clio's own order changes from run to run.

Generated files are byte-equal because nothing is hand-copied:
- `scripts/generate-workspace-templates.py --clio-dll <clio.dll>` copies the 262 template files the commands
  read from clio's `tpl/` folder (plain files next to clio.dll, not embedded resources) into
  `internal/workspace/templates/templates.zip` with `manifest.json` (path, size, SHA-256, mode); the zip is
  embedded and checked against the manifest on load, and `.gitattributes` keeps Git from touching it.
- `internal/workspace/dotnet.go`, `xmldoc.go`: Newtonsoft and System.Text.Json indented JSON with each one's
  escaping, `XmlDocument.Save`, `File.WriteAllText`, the host newline, ICU string order (checked against
  clio with 15 package names), File.Copy's mode and `chmod +x` on the workspace scripts.
- `create-workspace` reads the newest CreatioSDK version from api.nuget.org as clio does (`CreatioSdkOnline`,
  15 s); tests use a local feed (`workspace.NuGetBaseURL`).
- `add-item-model` output was checked against 19 model files clio generated from the same schema fixtures
  (`internal/workspace/testdata/models`).

## Known differences

- **link-from-repository, clio defect.** Over MCP, clio 8.1.0.142 builds `Link4RepoCommand` from its bootstrap
  container, whose Creatio address is `http://localhost`; the preparation step and the unlocked-package query
  answer `Connection refused (localhost:80)` whatever environment is named (reproduced here). This server
  sends those requests to the named environment; they were compared with clio's CLI
  (`clio link-from-repository -e <env>`) on the same fake site: same messages, byte-equal request bodies.
- **link-from-repository without a named environment** (`by-env-package-path`, or a path instead of a name):
  refused at the step where clio would first reach Creatio, so nothing destructive runs against an
  environment the caller did not name (`linkNoSiteText`). A Safe environment is refused too; clio does not.
- **generate-source-code**: clio formats a fractional timeout in minutes with the process culture (`1,5`),
  this server always `1.5`; the alias refusal lists unknown keys sorted (clio: request order), and with both
  `timeOut` and `timeout` this server answers the rename refusal where clio answers the range error.
- **add-item-model**: per-schema "not found" lines and parallel-read failures come in schema order; clio's
  order is that of its threads and changes from run to run. Requests are compared sorted for this reason.
- **push-workspace / restore-workspace**: the uploaded zip is compared by content (clio's zip carries file
  times and another deflate encoder); restore on a folder without workspace settings answers "Json file not
  found" (clio creates a workspace in its own working directory); a web farm (`StickySession` cookie) is
  refused before upload; on a .NET Framework environment from macOS or Linux this server warns instead of
  building the standalone packages.
- **add-package** reading the prefix from an environment: the existing `GetSchemaNamePrefix` client sends
  `sysSettingsNameCollection`, clio `SysSettingsNameCollection` (same for `get-schema-name-prefix`; Creatio
  accepts both, T22 live run).
- **new-ui-project** skips clio's package-list request, which only feeds a download offer a silent MCP call
  always declines.
- As for every command tool here: no `correlation-id` and no `notifications/message` log stream.

## Not verified

- Windows: everything builds for Windows and the Windows-only link tests exist, but nothing ran on Windows
  (CRLF output, backslash paths in .slnx, drive-letter paths, symbolic links — clio makes a symlink there
  too, not a junction).
- Against a real Creatio: push/restore, link preparation, generate-source-code and add-item-model ran only
  against fake sites; .NET Framework routing, developer-mode unlock, a failed backup, a failed login and
  calls longer than 150 s were not exercised.
- clio stops a link call after 120 s and imposes no limit on add-item-model reads; this server keeps a
  heartbeat for link and a 24 h cap for add-item-model.
